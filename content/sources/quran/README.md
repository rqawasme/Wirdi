# Quran source data

Nothing in this directory except this file and `ENCODING_REPORT.md` is committed.

Quran text and translations are licensed works. They are not redistributed through
this repository; each person who builds the content database downloads them from
QUL themselves. `.gitignore` enforces that.

Everything else in this directory (`surahs.json`, `ayahs.json`) is generated by
`content/scripts/import_quran.py` and must never be hand-edited.

## What you need to download

QUL (<https://qul.tarteel.ai/>) publishes its data as downloadable files, one per
resource, in SQLite and JSON. There is no bulk read API to pull from, so this is a
manual, one-off download. Go to <https://qul.tarteel.ai/resources>, find each
resource below, and download it.

**Prefer the SQLite (`.db` / `.sqlite`) download wherever it is offered.** A plain
JSON translation and a plain JSON transliteration are byte-for-byte the same shape
(`{"1:1": "…"}`), so the importer cannot tell them apart on its own and will make
you disambiguate with a flag. The SQLite exports name their tables, so they are
unambiguous.

This is the set the pipeline has actually been run against, with the filenames QUL
gave them:

| # | Resource on QUL | File | Table it provides |
|---|---|---|---|
| 1 | Quran metadata — **Ayah** | `quran-metadata-ayah.sqlite` | `verses` — ayah-level Uthmani text (QPC Hafs) |
| 2 | Translation — **Saheeh International** | `en-sahih-international-simple.db` | `translation` |
| 3 | Quran metadata — **Surah** | `quran-metadata-surah-name.sqlite` | `chapters` |
| 4 | Quran metadata — **Juz** | `quran-metadata-juz.sqlite` | `juz` |
| 5 | Quran metadata — **Hizb** | `quran-metadata-hizb.sqlite` | `hizbs` |
| 6 | Quran metadata — **Sajdah** | `quran-metadata-sajda.sqlite` | `sajdah` |
| 7 | **Transliteration** | `syllables-transliteration.db` | `transliterations` |

1–5 are required. Without #6 every `ayahs.sajdah` is `0`; without #7 every
`ayahs.transliteration` is `NULL`. Both columns tolerate that, so the build still
passes verification.

The importer identifies files by looking inside them, not by their names, so you do
not need to rename anything. If two downloads look like the same kind of resource it
stops and tells you to pick one with an explicit flag.

## Where to put them

```
content/sources/quran/downloads/
```

Then check what was recognised before importing:

```bash
python3 content/scripts/import_quran.py --check
```

Any file it cannot place is listed as `UNRECOGNISED` **together with its tables and
columns**, so you can see immediately what it actually is.

## Watch out: "Uthmani script" is word-by-word

QUL's Quran-script downloads (the ones named for a script, e.g. `uthmani.db`) are
**word-by-word**: one row per word in a `words` table, 83,668 rows, not one row per
ayah. `--check` reports these as `word_script` and does not use them.

Ayah-level Uthmani text comes from the **Quran metadata → Ayah** resource
(`quran-metadata-ayah.sqlite`), whose `verses.text` is the QPC Hafs Uthmani text.
That is what the pipeline uses by default.

If you would rather have the word-export's orthography, pass it explicitly:

```bash
python3 content/scripts/import_quran.py --script content/sources/quran/downloads/uthmani.db
```

and the importer rebuilds each ayah by joining its words in order. Be aware the two
are **different Uthmani conventions**, not the same text formatted differently — they
disagree on all but 62 of the 6,236 ayahs. The metadata-ayah text uses the Madani
mushaf conventions (U+06E1 in place of sukun, U+0655/0656/0657/065E, U+06E4); the
word export uses plain sukun U+0652, U+0622 and a different set of pause marks. Both
are standard Unicode with no Private Use Area codepoints.

## The ayah number is part of the text

Every ayah in the metadata-ayah export **ends with its own ayah number**, written in
Arabic-Indic digits and preceded by a no-break space — all 6,236 of them, with no
exceptions and no digits anywhere else in the text.

`text_uthmani` keeps them, so the column stays byte-identical to the source. If the
app renders its own ayah numbering, import with:

```bash
python3 content/scripts/import_quran.py --strip-ayah-numbers
```

`text_simple` never contains them either way.

## Mushaf page numbers

`ayahs.page` is left `NULL` unless a page number can be found, and none of the
downloads above carries one.

QUL's **mushaf layout** export is indexed by word (`first_word_id`, `last_word_id`),
not by ayah, so it cannot supply per-ayah page numbers without also importing the
full word-level dataset. Two things do work:

- Some QUL script exports (the glyph-based `code_v1` / `code_v2` scripts) carry a
  `page_number` column per verse. If your script download has one, it is picked up
  automatically.
- Otherwise pass `--pages <file>`, where the file is JSON mapping verse keys to page
  numbers: `{"1:1": 1, "2:1": 2, …}`.

Page numbers are not needed for v1.

## English surah names

QUL's chapter export has `name_arabic`, `name_simple` and `name` (a transliteration
with diacritics) — but no English *translation* of the surah name. So by default
`surahs.name_english` falls back to the plain transliteration and the importer prints
a warning.

To get real English names, supply your own file:

```bash
python3 content/scripts/import_quran.py --english-names my-names.json
```

where `my-names.json` is `{"1": "The Opening", "2": "The Cow", …}` covering all 114
surahs. The importer refuses a partial list.

## A note on `has_bismillah`

`surahs.has_bismillah` is derived as "1 for every surah except 9", **not** from QUL's
`bismillah_pre`. QUL sets `bismillah_pre` false for surah 1 as well, because there the
basmala is ayah 1 rather than a heading above it. That is correct for QUL's purposes
and wrong for ours, which is why the importer ignores that column.
