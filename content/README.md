# Wirdi content pipeline

Turns hand-authored JSON plus imported Quran data into `content/build/content.db`,
the SQLite database the Flutter app bundles.

```
content/
  sources/          everything here is built into content.db
    quran/          committed; generated by import_quran.py, never hand-edited
    adhkar/         hand-authored, one file per group
    collections/    hand-authored, one file per collection
    sources.json    hadith and book references; absent until one is authored
    VERSION         content version stamped into the database
  examples/         the worked examples — NOT built, see examples/README.md
  schemas/          JSON Schema for the hand-authored formats
  scripts/          the four pipeline scripts
  build/
    content.db      output, gitignored
```

Only `sources/` reaches the database. `examples/` holds a complete, valid set of
authored content demonstrating every feature of the format, kept out of the build
because its text is the placeholder sentinel — see
[`examples/README.md`](examples/README.md).

## Running it

```bash
pip install -r content/requirements.txt

python3 content/scripts/validate_json.py    # schema check (build runs this too)
python3 content/scripts/build_content.py    # -> content/build/content.db
python3 content/scripts/verify_content.py   # invariants, exits non-zero on failure
```

The Quran JSON is committed, so that sequence works on a fresh clone.
`import_quran.py` regenerates it from QUL exports and is only needed when
refreshing the Quran data — see [`sources/quran/README.md`](sources/quran/README.md).

While authoring, the loop you want is:

```bash
python3 content/scripts/validate_json.py && \
python3 content/scripts/build_content.py && \
python3 content/scripts/verify_content.py
```

## Ids are permanent

The database is rebuilt from source regularly. A user's saved collections point at
these ids, so an id that shifts between builds silently repoints saved content at
something else. There is no `AUTOINCREMENT` anywhere in the database, and
`verify_content.py` fails if any appears.

| Id | Rule |
|---|---|
| `ayahs.id` | computed: `surah_number * 1000 + ayah_number` |
| `adhkar.id` | explicit, written by you |
| `collections.id` | explicit, written by you |
| `sources.id` | explicit, written by you |
| `collection_items.id` | computed: `collection_id * 1000 + position` |

Two consequences worth knowing:

- **A collection is capped at 999 items.** The build fails loudly past that rather
  than colliding with the next collection's ids.
- **Reordering a collection's items changes their `collection_items.id`s**, because
  position is assigned in file order. That is fine — those ids are internal.
  Changing a `dhikr` id is not fine.

Duplicate ids are rejected across *all* files, not just within one file.

## Authoring adhkar

One file per group in `sources/adhkar/`, named after the group (`morning.json`,
`evening.json`). The `group` field is organisational and is not written to the
database.

```json
{
  "group": "example",
  "adhkar": [
    {
      "id": 1001,
      "text_arabic": "PLACEHOLDER — to be filled by Rashid",
      "translation": "PLACEHOLDER — to be filled by Rashid",
      "default_count": 1
    },
    {
      "id": 1002,
      "text_arabic": "PLACEHOLDER — to be filled by Rashid",
      "translation": "PLACEHOLDER — to be filled by Rashid",
      "transliteration": "PLACEHOLDER — to be filled by Rashid",
      "default_count": 33,
      "source_id": 1,
      "benefits": "PLACEHOLDER — to be filled by Rashid"
    }
  ]
}
```

Required: `id`, `text_arabic`, `translation`, `default_count`.
Optional, and **omitted entirely when unused**: `transliteration`, `source_id`,
`benefits`, `notes`. Every `source_id` must resolve against
`sources/sources.json`.

## Authoring collections

One file per collection in `sources/collections/`. Items are listed inline, in
recitation order — there is no separate join file.

```json
{
  "id": 1,
  "name_arabic": "PLACEHOLDER — to be filled by Rashid",
  "name_english": "PLACEHOLDER — to be filled by Rashid",
  "description": "PLACEHOLDER — to be filled by Rashid",
  "author": "PLACEHOLDER — to be filled by Rashid",
  "type": "wird",
  "sort_order": 10,
  "items": [
    { "dhikr": 1001 },
    { "dhikr": 1002, "count": 100 },
    { "ayah": "2:255" },
    { "ayah": "2:285-286" },
    { "surah": 112, "repeat_group": 1, "repeat_group_count": 3, "note": "PLACEHOLDER — to be filled by Rashid" },
    { "surah": 113, "repeat_group": 1, "repeat_group_count": 3 },
    { "surah": 114, "repeat_group": 1, "repeat_group_count": 3 },
    { "dhikr": 1003, "note": "PLACEHOLDER — to be filled by Rashid" }
  ]
}
```

`type` is one of `wird`, `dhikr_set`, `surah_set`.

### Items

Each item is **exactly one** of:

| Written as | Becomes | Notes |
|---|---|---|
| `{ "dhikr": 1001 }` | `item_type` `dhikr`, `item_id` 1001 | must exist in `sources/adhkar/` |
| `{ "ayah": "2:255" }` | `item_type` `ayah`, `item_id` 2255 | id computed for you |
| `{ "ayah": "2:285-286" }` | two `ayah` items | inclusive range, within one surah |
| `{ "surah": 36 }` | `item_type` `surah`, `item_id` 36 | the whole surah |

Ayah references are checked against the real surah length at build time, so
`{"ayah": "2:300"}` fails with `surah 2 has 286 ayahs` rather than producing a row
that points at nothing.

### Optional item fields

Omit them when unused; do not write `null`.

- **`count`** — repetitions of this one item, stored as `count_override`. For a
  dhikr it overrides that dhikr's `default_count`.
- **`repeat_group`** / **`repeat_group_count`** — a block of consecutive items
  repeated together. In the example above, the three surahs are recited as a block,
  three times over. Both fields are required together; items sharing a group must
  be **contiguous** and must **agree** on the count. The build enforces all three
  rules.
- **`note`** — a rubric shown with that item.

The worked example above is a real, valid file: it is
`examples/collections/example.json`, and it exercises every feature of the format.
Its companion is `examples/adhkar/example.json`. Copy them as starting points —
into `sources/`, where the build will pick them up.

That example builds to nine `collection_items` rows, not eight, because the ayah
range expands:

| position | item_type | item_id | count_override | repeat_group |
|---:|---|---:|---:|---:|
| 1 | dhikr | 1001 | | |
| 2 | dhikr | 1002 | 100 | |
| 3 | ayah | 2255 | | |
| 4 | ayah | 2285 | | |
| 5 | ayah | 2286 | | |
| 6 | surah | 112 | | 1 |
| 7 | surah | 113 | | 1 |
| 8 | surah | 114 | | 1 |
| 9 | dhikr | 1003 | | |

## Authoring sources

`sources/sources.json` holds the hadith and book references that `adhkar.source_id`
points at. There is no such file yet: no real reference has been authored, and
`build_content.py` treats a missing one as no sources rather than an error, so
create it when the first citation exists. `examples/sources.json` shows the
format.

```json
{
  "sources": [
    {
      "id": 1,
      "collection": "PLACEHOLDER — to be filled by Rashid",
      "reference": "PLACEHOLDER — to be filled by Rashid",
      "grading": "PLACEHOLDER — to be filled by Rashid"
    }
  ]
}
```

Required: `id`, `collection`, `reference`. Optional: `grading`, `full_text`.

## When validation fails

`validate_json.py` names the file, the JSON path and what it expected, and falls
back to the schema's own description as a hint:

```
  content/examples/collections/example.json
    at $.items[4]
    expected exactly one of [dhikr, ayah, surah], found 2 of them: dhikr, ayah

  content/examples/adhkar/example.json
    at $.adhkar[0].default_count
    expected a value >= 1, found 0
    hint: How many times this dhikr is said by default. A collection may override it per item with "count".
```

Malformed JSON — a trailing comma, usually — is reported with the line, the column
and the offending source line rather than a traceback.

Structural problems are `validate_json.py`'s job; anything needing cross-file
knowledge (does this dhikr exist? is this ayah in range?) is `build_content.py`'s.

## The database

| Table | Rows |
|---|---|
| `surahs` | 114 |
| `ayahs` | 6,236 |
| `adhkar` | one per authored dhikr |
| `sources` | one per reference |
| `collections` | one per authored collection |
| `collection_items` | one per item, after ayah ranges expand |
| `meta` | `schema_version`, `content_version`, `built_at`, `quran_source`, `translation_edition`, `content_checksum` |

`ayahs.text_simple` is `text_uthmani` with diacritics stripped and alef variants
normalised, for search matching later. Search is not a v1 feature; the column costs
nothing at build time and means adding search later needs no content migration. The
exact transformation is documented in `simplify_arabic()` in `import_quran.py`.
Against the real QPC Hafs text it reduces to 33 codepoints: the Arabic letters, the
hamza-carrying forms, teh marbuta and the space. No combining mark survives it.

`ayahs.text_uthmani` keeps the trailing ayah number that QUL bakes into each ayah
(Arabic-Indic digits after a no-break space). Import with `--strip-ayah-numbers` if
the app should render its own numbering instead.

### Knowing when content changed

Every build prints a SHA-256 over the content rows, taken in a fixed table and row
order with `meta` excluded (so `built_at` does not perturb it). The same sources
always produce the same checksum, and it is stored in `meta.content_checksum`.

```
  content checksum     7f7ffd67e4e2b1534faa9a57a06d62b56cefc5180088d6aa32d99b38227dec04
```

Same checksum, same content. Different checksum, something really changed.

## Never invent religious text

No Quranic text, hadith text or dhikr text may be written from memory — not as an
example, not as a placeholder, not as a test fixture. Everything must come from a
verified source. Where sample content is needed, use the literal string
`PLACEHOLDER — to be filled by Rashid`, as the example files do.
